## 실시간 차트 데이터 파이프라인 구성

- 기존 프로젝트에서 담당했던 실시간 차트 기능을 구현 및 배포

## Architecture

![Stock 프로젝트 아키텍처](./media/stock/stock-arch/stock-architecture.svg)

## Presentation & Routing

- HTTPS 기반 단일 진입점(Single Entry Point) 구축:
  - Nginx를 활용해 모든 외부 요청을 443 포트로 단일화하여 인프라 복잡성을 은닉하고 보안을 강화했습니다
  - HTTP(80) 요청에 대한 자동 HTTPS(443) 리다이렉션 설정을 적용하여, 모든 사용자 데이터 통신이 암호화된 채널을 통해서만 이루어지도록 강제했습니다.
- 경로 기반 라우팅:
  - 요청 경로에 따라 정적 자원, API요청, 웹소켓 연결을 각각의 전용 컨테이너로 분기하는 구조
- External Proxy 확장성:
  - 향후 인스턴스 시스템 부하를 고려하여, Nginx 설정 변경만으로 다른 프로젝트 서비스에 트래픽 넘기는 방식 가능

## Application Layer

- 어플리케이션 컨테이너화:
  - 프론트엔드, 백엔드, 데이터 수집, 데이터 전파를 각각 독립된 컨테이너로 분리하여 마이크로서비스 지향적 구조 설계
- Internal DNS:
  - IP를 통한 내부 통신 대신 도커 내부 DNS를 활용해 통신함으로써, 컨테이너 재시작 시에도 끊김 없는 연결성 확보
- OutBound 통신:
  - 외부 API와 통신하는 데이터 수집 서비스는 프록시 거치지 않고 직접 연결하여 네트워크 지연 최소화

## Live Streaming Pipeline

- 이벤트 기반 아키텍처 Kafka 도입:
  - Kafka를 중앙 브로커로 두어 데이터 생산과 전파를 관리하고, 대량의 메세지 스트림을 중계
- Fan-out 기반 데이터 전파:
  - Consumer 컨테이너 내부에 구현된 웹소켓 서버가 다수의 클라이언트들에게 데이터를 전파하도록, 인메모리 기반의 팬아웃 구조 적용하여 서버 자원 효율성 확보
- 비동기 데이터 파이프라인 최적화:
  - 데이터 수집을 다중화하고, 전파 흐름을 비동기적으로 처리하여, 병목 현상 최소화

## Data & Infra

- Docker Bridge Network:
  - 인스턴스의 내부 통신을 도커의 가상 망으로 격리하여, 외부에서 내부 서비스로 직접 접근하는 것 방지
- Volume Mount를 통한 영속성 확보:
  - 호스트 시스템의 db파일을 컨테이너에 매핑하여, Stateless 컨테이너 환경에서도 데이터 상태 보존

## 📌 고민

### 💡 문제점(Challenge)

- 증권사 Open API(WebSocket)를 통해 수집되는 실시간 체결 데이터는 변동성이 커질 경우 급증하기 때문에
  **단일 파이프라인으로 구조로는 특정 체결 데이터에의해 병목이 발생하게 되면** 나머지 종목 체결 데이터가 줄줄이 밀리는 연쇄 지연 발생

### 🛠️ 해결 방안(Solution)

- 데이터 수집 단의 병렬화
  - Producer 역할을 수행하는 프로그램을 별도 컨테이너에서 구동해 **수집 속도 개선**
- 토픽 기반 데이터 샤딩
  - 2개의 토픽으로 티커들은 분리하여 단일 토픽에 모든 트래픽이 몰릴 경우 발생하는 브로커의 **부하를 분산시킴**
  - 추가적으로 균등한 부하를 목적으로 Grafana, Prometheus를 활용한 kafa-monitoring 시스템을 활용하여 각각의 토픽별로 **균등한 트래픽**을 유지하는지 모니터링 기능 추가 시킴
    ![Grafana](./media/stock/stock-imgs/stock-grafana.png)
- 메시지 키 기반 순서 보장
  - 토픽 내에서 티커를 Key로 구분하여 체결 종목 데이터의 **인과 관계를 보장**

### 💡 문제점(Challenge)

- 초기 컨슈머 설계 단계에서는 클라이언트가 접속할 때 마다 해당 요청을 처리하기 위해 독립적인 컨슈머를 **매번 새로 생성하여 할당**하는 방식이었고, 접속자 수가 늘어날수록 브로커와의 커넥션이 선형으로 증가하기에 서버 자원 소모가 극심해 질 수 있었고, 동일한 종목을 조회하는 여러 클라이언트가 있어도 각 컨슈머가 브로커로부터 동일한 데이터를 중복해서 수신하는 네트워크 낭비도 발생했음

### 🛠️ 해결 방안(Solution)

- 컨슈머 계층의 독립:
  - 클라이언트의 접속 여부와 상관 없이, 시스템에서 필요한 데이터를 topic, ticker별로 고정된 수의 컨슈머만 운용하도록 설계 변경
- 비동기 태스크 관리:
  - asyncio.gather을 이용해서 클라이언트들에게 BroadCast하는 방식으로 로직을 병렬화 수행, 이를 통해 특정 클라이언트의 네트워크 지연이나 예외가 전체 파이프라인에 병목을 일으키지 않도록 격리
- 인메모리 팬아웃(Fan-out) 구조 구현:
  - 컨슈머가 브로커로부터 데이터를 딱 한 번 읽어오면, 이를 서버 내 전역 상태에서 관리하는 모든 클라이언트들에게 비동기로 전파하는 구조 구현
